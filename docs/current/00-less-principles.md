# Less · 产品原则

状态：当前项目基线  
更新：2026-09-22  
适用：产品讨论、内容编辑、设计与开发决策

## 1. Less 为什么存在

**Less — Read less. Know more.**

AI 信息很多，人的注意力有限。Less 帮助读者找到、筛选并理解真正值得知道的变化，以更少阅读获得更清楚的认识，并让这些认识随时间积累。

Less 以人的注意力为中心。用户打开产品，应能轻松知道值得关注什么、为什么值得关注，以及去哪里查看原始依据。

## 2. 当前方向

**把获取内容当能力，把理解内容当产品。**

- 内容发现、阅读、筛选、去重、核验与提炼，由 Content Skill / Agent 配合工具完成。
- Less 软件负责保存、组织、连接、检索和呈现值得留下的内容。
- 核心内容对象是 Brief、Topic、Source，以及必要的时间信息。
- 从 Today 开始；Topics、Ask、Signal 等能力随内容积累和真实需求自然生长。

**AI 负责把混乱变成结构，软件负责让结构产生长期价值。**

旧的重型 Content Engine 路线已废弃，不再作为正式产品架构继续演进。这是方向调整，不只是隐藏旧后台或简化其操作界面。

## 3. 什么值得留下

内容至少满足 **Important OR Useful** 中的一项，不要求两项同时满足。

**Important：重要。** 对 AI 能力、产品使用方式、成本、可获得性或行业方向有实质影响，值得读者更新认识。判断应说明具体改变了什么、影响谁；发布者知名或传播广泛本身不构成重要性。

**Useful：有用。** 能帮助读者完成具体任务、做出选择或减少试错，例如可用工具、可复现方法、清晰教程或有依据的实践经验。判断应说明适用对象、使用场景和限制。

这是一项编辑判断，不是一套要求用户逐项打分的评分系统。没有足够价值的内容可以不收；某一天没有值得留下的新内容，也可以为空。

## 4. 不变的编辑原则

### 原始来源优先

优先阅读官方发布、文档、论文、代码仓库、原作者文章或直接记录。媒体与社区可用于发现线索、补充背景和不同观点。

原始来源不等于所有主张都已被独立证明。厂商性能声明、作者自述和实际验证结果需要区分。无法确认的内容明确标注，不用确定语气填补信息缺口。

### 事实、意义与判断分开

每条 Brief 应讲清楚：发生了什么、为什么值得关注、Less 怎么看、依据来自哪里。事实要有来源；推断要标明是推断；没有额外判断时不必强写观点。

### 克制可信

标题准确、表达简洁，不制造焦虑，不夸大突破，不用泛泛的趋势判断替代具体信息。优先解释影响和边界，而不是复述宣传语。

### 少而精

合并重复报道，过滤没有实质增量的发布。以是否值得读者花时间为准，不以条数、更新频率或来源覆盖率为目标。允许简短，但不能压缩掉关键条件和不确定性。

## 5. 产品与工程原则

**复杂度必须由真实需求赢得。**

- 先跑通少量真实内容的获取、保留与阅读，再决定需要什么功能。
- 能由 Skill、Prompt、现成工具和轻量文件完成的工作，先这样完成。
- 只有真实使用暴露出稳定性、规模、速度、权限或协作问题时，才增加对应软件能力。
- 优先保存有长期价值的结果、来源、时间和关系；不把 Agent 的中间推理、评分与工作步骤默认建成业务对象。
- 用户应主要阅读和探索内容。必要的人工编辑保持简单，不要求用户运营一套情报工作流。

提出新能力前，先回答：谁在什么场景遇到了什么问题？现有简单方式为何不够？最小改变是什么？如何从实际使用判断它有价值？

## 6. 如何判断 Less 是否有用

先观察真实体验：读者能否快速找到值得关注的内容，能否理解其意义并追溯来源，是否愿意再次打开，过去保留的内容是否帮助回答新问题。

这些是验证方向，不要求先建设指标平台。采集量、数据库表数、后台功能数量和已投入的开发时间，都不能替代产品价值。
