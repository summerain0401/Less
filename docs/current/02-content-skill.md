# Less · Content Skill

状态：当前项目基线  
更新：2026-09-24
用途：供执行内容任务的 Skill / Agent 使用的编辑规范；不代表已安装或运行的自动化任务

## 1. 任务与边界

通过 **Find → Filter → Verify → Summarize**，把分散的信息整理为少量值得保留的 Brief。

遵循 **Read less. Know more.** 与 **Important OR Useful**。优先原始来源，保持克制可信，分开事实与判断。

本 Skill 交付内容及必要的来源说明。它不要求建立采集平台、事件聚类库、证据系统、评分后台或编辑审批流程；也不把中间推理过程作为产品数据交付。

## 2. 任务输入

每次运行使用当前任务提供的信息：

- 时间范围及所用时区。
- 关注主题、读者场景或具体问题。
- 用户指定来源、项目首选来源清单及允许使用的搜索、浏览等工具。
- 已保留 Brief 或近期标题、链接，用于去重；若无法取得，说明去重范围受限。
- 可选条数上限。上限不是必须完成的数量。

缺少非关键参数时采用合理范围并简短说明；影响任务判断时再澄清。不把来源列表理解成必须穷尽的采集清单，也不声称覆盖了所有重要信息。

## 3. Coverage Map：我们观察什么

沿用[原产品蓝图第 5 节](../archive/content-engine-prototype/01-product-blueprint.md)的编辑观察范围。Coverage 是选题视角，不等于前台栏目或 Brief 的 Topic；软件暂未提供 Signal 页面，也不意味着停止观察跨事件的变化。

| 核心 Coverage | 观察问题 | 典型进入理由 |
| --- | --- | --- |
| Frontier | AI 的能力边界和行业方向改变了什么？ | 模型、推理、多模态、Agent、开源或基础设施的实质进展 |
| Builders | 人们如何真正构建和使用 AI？ | 工程方法、AI Coding、Context / Memory、工具调用、工作流与真实实践 |
| Voices | 影响 AI 发展的人在思考什么，其判断如何变化？ | 有实质观点和完整语境的访谈、演讲、长文、研究或发言 |
| Signals | 分散事件共同指向什么变化？ | 对跨事件、跨时间的判断持续积累正反证据 |

Business / Science / Robotics / Society 选择性覆盖，以 Important 门槛判断；不设日常填充配额。AI Tools / Products 不单列 Coverage，按其能力变化、实践用途或长期信号进入上述视角。普通产品发布、融资快讯、跑分排名和人物动态没有独立收录理由。Voices 关注观点及其语境，而非名人身份。

## 4. Source Map：我们靠什么观察

沿用[原产品蓝图第 6 节](../archive/content-engine-prototype/01-product-blueprint.md)的来源角色。具体内容节点可以是工程博客、仓库 Releases、研究者个人博客或专业栏目；组织名、网站名不等于质量均匀的单一来源。

| 来源角色 | 主要作用 | 使用边界 |
| --- | --- | --- |
| Primary | 发布、研究、代码、数据等事实源头 | 优先回溯；官方自述仍有适用范围和利益立场 |
| People | 思想、经验与方向判断的源头 | 结合人物的具体领域和依据判断，不把人物整体权威化 |
| Builders | 实践方法、工程复盘、开源实现 | 查方法、条件、失败案例与可复现性 |
| Intelligence | 专业媒体、研究机构、独立分析的发现、调查、背景与交叉验证 | 转述需回溯；原创调查或测量可构成相应主张的一手证据 |
| Discovery | 社区讨论、榜单、社交平台等线索入口 | 热度只提示值得检查，不证明事实 |

角色用于选择观察入口，不是可信度排名。同一节点可以服务多个角色；Brief 的 `sources[].primary` 必须按具体材料及其支撑的主张判断，不能由节点角色自动决定。官方政策和标准属于相应机构的一手来源，另按任务主题检索。

原蓝图中的 Source Registry、访问节奏和质量反馈属于旧采集方案；当前用[版本化首选来源清单](../../.agents/skills/less-content/references/preferred-sources.md)保留具体观察入口，并按任务动态扩展，不恢复自动采集或来源后台。

## 5. Find：找到值得核验的线索

使用混合来源策略：先处理用户明确指定的来源，再从项目首选来源清单中选择一小批与主题相关的入口，覆盖不足或需要交叉验证时再扩展搜索。首选来源是搜索起点，不是白名单、完整覆盖承诺或可信度评分；不要求每次遍历整份清单。

宽泛日报应在存在相关内容时兼顾相关 Coverage、多个独立组织和不同来源角色，不能只从厂商公告或版本日志挑选。窄主题任务只检查相关来源。扩展到清单外来源时，优先回到官方发布、具体文档、论文、仓库或原作者页面，并在任务说明中注明实际检查范围。

优先查看官方公告与文档、论文原文、项目仓库与 Release、原作者文章和直接实践记录。专业媒体、社区讨论、社交平台及通讯可帮助发现线索、寻找独立验证和补充背景。与观察范围直接相关的人物社媒账号也可作为固定入口；选择依据是其在特定领域持续提供第一手信息，而非身份或关注人数。同一人物的博客与社媒视为一个编辑节点。

宽泛扫描按实际相关内容兼顾 Frontier、Builders、Voices，并从跨事件、跨时间的材料中寻找支持或反驳 Signals 的证据；不为某一视角设来源或 Brief 条数配额。社媒原帖可支撑发帖人本人的观点和直接经历；转发、预告、产品可用性或效果主张应追到具体原文、文档、发布记录或其他证据。打不开完整帖文时只作为线索。

来源配置保持轻量：稳定标识、名称、地址、角色、关注主题、使用备注与已知偏向即可。不维护采集频率、健康分、权威度矩阵等完整运营配置。当前首选来源清单由仓库级 `less-content` Skill 版本化维护，不代表来源已自动接入或其内容已经核验。

## 6. Filter：判断是否值得留下

对每条内容先回答：

1. 有什么明确的新事实、实质变化或可用知识？
2. 它为什么 Important 或 Useful，具体影响谁？
3. 相对已保留内容，增量是什么？

Important 关注实质影响，例如能力边界、成本、开放范围、使用方式的改变。Useful 关注具体用途，例如能操作的方法、可复现实践和有明确适用条件的工具。

默认跳过纯宣传、标题党、无实质增量的版本噪声、重复转载、只有情绪的观点，以及无法支撑核心主张的传闻。品牌名气、热度和转发量不能单独证明价值。

同一变化的多篇报道尽量合成一条 Brief，优先引用原始来源；同一人物跨博客、社媒及官方渠道重复表达的同一主张也应合并。只有存在新的实质进展才新增内容。去重可依据原文链接、标题与语义判断，无需持久化 Event 或 Cluster 对象。

## 7. Verify：核对事实与边界

- 尽量打开具体原文，核对标题之外的正文、发布日期、版本、适用范围及关键限制。
- 社媒帖文要核对账号身份、原帖链接、发帖日期、完整措辞及上下文；截图、搜索摘要和二次转述不能替代原帖。
- 区分发布、预告、演示、测试开放与正式可用；不要把计划写成已经发生。
- 涉及数字、性能、价格或对比时保留影响结论的条件；对厂商或作者声明注明归属。
- 对争议或重要效果主张，按需要寻找独立验证。多篇转载同一个出处不算多份独立证据。
- 来源冲突时说明分歧；核心事实不能确认时暂不收录为正式 Brief。
- 无法访问原文时如实说明。搜索摘要和转载可以提供线索，但不能伪装成已经阅读全文的核验结果。
- 不编造链接、日期、引文、实验结果或使用体验。

核验把握采用简明分类：

| `confidence` | 使用含义 |
| --- | --- |
| `high` | 核心事实已由直接来源清楚支持，关键范围与条件明确 |
| `medium` | 核心事实有可靠支持，但存在必须向读者说明的局限 |
| `low` | 核心事实尚缺充分支持或存在未解决冲突；仅作为待核验草稿，不进入正式 Today |

把握度针对核心事实，不代表认可所有宣传结论，也不等于预测未来的信心。未知项写进 `uncertainty`，不生成精密分数。

## 8. Summarize：写成 Brief

每条 Brief 包含以下可阅读结构：

**标题**：直接说清变化或用途，不夸大。

**发生了什么（What happened）**：让没有读过原文的人只看这一栏，也能说清具体发生了什么。先交代主体和核心变化，再补足理解变化必需的背景或此前状态、实际新增或改变的内容、发布与可用状态、适用对象及关键条件。方法类内容要说明解决的问题、做法和已观察到的结果；研究类内容要说清研究对象、方法或证据与结论。只写“发布了新模型”“提升了性能”不够；有数字或效果主张时说明是谁测得、在什么条件下，不把自述写成独立证实。可分短段，不设固定字数，以读者不必打开来源补全基本事实为准。

**为什么值得关注（Why it matters）**：明确重要性或实用性、受影响的人和适用场景。不用“推动行业发展”等空话代替解释。

**Less 怎么看（Our take）**：仅在有帮助时提供判断、联系或推断，说明依据及边界。没有额外洞察时留空，不强写趋势。

**来源与限制**：列出具体原文链接、日期和必要的不确定性。不同主张来自不同页面时，正文应能分清对应来源。

`what_happened` 只写事实及必要背景，不把重要性和 Less 判断混入其中；后两者分别放在 `why_it_matters` 和 `our_take`。写完后自检：读者是否知道“原来怎样、现在具体怎样、目前能否使用或复现、哪些仍只是发布者的说法”？缺少核心细节时继续核验，不能用概括性话语掩盖信息不足。

默认使用清楚、克制的中文，保留有辨识价值的英文名称。信息足够即止，不为固定字数扩写，也不为简短省略关键条件。

## 9. 统一输出约定

以下模板是与软件层衔接的轻量内容约定，不要求特定数据库或工具。花括号内容需要替换；不得把占位内容当作真实 Brief。

```yaml
id: "{稳定标识}"
title: "{准确标题}"
published_at: null
topics:
  - "{主题}"
important: true
useful: false
confidence: "high"
sources:
  - name: "{来源名称}"
    url: "{具体原文链接}"
    type: "{official_docs / release / paper / blog / media / other}"
    primary: true
    published_at: null
what_happened: "{主体、此前状态、具体变化、可用范围及必要条件}"
why_it_matters: "{重要性或用途及适用对象}"
our_take: null
uncertainty: null
```

- `important` 和 `useful` 根据内容填写，至少一项为 `true`，两项也可以同时为真。
- `sources` 至少包含一个实际支撑核心内容的具体链接。`primary` 表示是否为原始来源，不表示它天然客观或已经独立验证。
- 顶层 `published_at` 使用主要来源的发布时间；各来源可分别记录日期。只有日期时使用 `YYYY-MM-DD`，有可靠时间时使用带时区的 ISO 8601；未知填 `null`，不以运行日期补造。
- `id` 在内容保留和更新时保持稳定；已有内容的更正应沿用原标识。
- `our_take`、`uncertainty` 无内容时填 `null`。已知限制必须写明，不能以空值掩盖。
- 正式保存端补充 `created_at`。事件时间、更新日期、实体标签等仅在确有需要时增加，与架构文档保持一致。

最终交付可以是一组 Markdown Brief 或结构化记录，但字段含义保持一致。已核验且值得保留的内容与低把握待核验草稿分开交付，避免误收录。

## 10. 完成一次任务

交付前做一次简短检查：内容是否有价值，核心事实是否有依据，是否重复，标题是否准确，判断是否与事实分开，链接和时间是否真实，限制是否说明。

这是 Agent 的工作检查，不是要求用户操作的 Quality Gate。可随结果附一段任务说明，写明实际检查的范围、访问限制和是否存在待核验事项；无需保存逐条淘汰记录或内部推理。

人工如需介入，只应面对内容本身：保留、跳过或编辑。纠正已保留内容时更新对应 Brief，并按需要注明更正；不默认增加完整版本审批系统。

允许交付零条。用户没有授权发布或安排运行时，生成草稿不等于已经入库、发布或建立自动任务。

## 11. 维护方式

根据真实内容任务暴露的问题，调整来源、主题、筛选规则和表达方式。优先改进 Skill；只有简单工具和编辑规则持续无法解决具体问题时，才提出软件需求。

本文件延续原蓝图的 Coverage Map、Source Map 和仍然有效的编辑方法，不承接旧 Content Engine 的对象体系与流程。长期原则以 `00-less-principles.md` 为准，产品职责以 `01-less-lite-architecture.md` 为准。
