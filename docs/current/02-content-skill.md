# Less · Content Skill

状态：当前项目基线  
更新：2026-09-22  
用途：供执行内容任务的 Skill / Agent 使用的编辑规范；不代表已安装或运行的自动化任务

## 1. 任务与边界

通过 **Find → Filter → Verify → Summarize**，把分散的信息整理为少量值得保留的 Brief。

遵循 **Read less. Know more.** 与 **Important OR Useful**。优先原始来源，保持克制可信，分开事实与判断。

本 Skill 交付内容及必要的来源说明。它不要求建立采集平台、事件聚类库、证据系统、评分后台或编辑审批流程；也不把中间推理过程作为产品数据交付。

## 2. 任务输入

每次运行使用当前任务提供的信息：

- 时间范围及所用时区。
- 关注主题、读者场景或具体问题。
- 已有来源列表及允许使用的搜索、浏览等工具。
- 已保留 Brief 或近期标题、链接，用于去重；若无法取得，说明去重范围受限。
- 可选条数上限。上限不是必须完成的数量。

缺少非关键参数时采用合理范围并简短说明；影响任务判断时再澄清。不把来源列表理解成必须穷尽的采集清单，也不声称覆盖了所有重要信息。

## 3. Find：找到值得核验的线索

从一小批与主题相关的来源开始，按需要扩展搜索。

优先查看官方公告与文档、论文原文、项目仓库与 Release、原作者文章和直接实践记录。专业媒体、社区讨论、社交平台及通讯可帮助发现线索、寻找独立验证和补充背景。

来源配置保持轻量：名称、地址、类型、关注主题、备注即可。不维护采集频率、健康分、权威度矩阵等完整运营配置。本文不预设一份已核验、已接入的来源名单。

## 4. Filter：判断是否值得留下

对每条内容先回答：

1. 有什么明确的新事实、实质变化或可用知识？
2. 它为什么 Important 或 Useful，具体影响谁？
3. 相对已保留内容，增量是什么？

Important 关注实质影响，例如能力边界、成本、开放范围、使用方式的改变。Useful 关注具体用途，例如能操作的方法、可复现实践和有明确适用条件的工具。

默认跳过纯宣传、标题党、无实质增量的版本噪声、重复转载、只有情绪的观点，以及无法支撑核心主张的传闻。品牌名气、热度和转发量不能单独证明价值。

同一变化的多篇报道尽量合成一条 Brief，优先引用原始来源；只有存在新的实质进展才新增内容。去重可依据原文链接、标题与语义判断，无需持久化 Event 或 Cluster 对象。

## 5. Verify：核对事实与边界

- 尽量打开具体原文，核对标题之外的正文、发布日期、版本、适用范围及关键限制。
- 区分发布、预告、演示、测试开放与正式可用；不要把计划写成已经发生。
- 涉及数字、性能、价格或对比时保留影响结论的条件；对厂商或作者声明注明归属。
- 对争议或重要效果主张，按需要寻找独立验证。多篇转载同一个出处不算多份独立证据。
- 来源冲突时说明分歧；核心事实不能确认时暂不收录为正式 Brief。
- 无法访问原文时如实说明。搜索摘要和转载可以提供线索，但不能伪装成已经阅读全文的核验结果。
- 不编造链接、日期、引文、实验结果或使用体验。

核验把握采用简明分类：

| `confidence` | 使用含义 |
| --- | --- |
| `high` | 核心事实已由直接来源清楚支持，关键范围与条件明确 |
| `medium` | 核心事实有可靠支持，但存在必须向读者说明的局限 |
| `low` | 核心事实尚缺充分支持或存在未解决冲突；仅作为待核验草稿，不进入正式 Today |

把握度针对核心事实，不代表认可所有宣传结论，也不等于预测未来的信心。未知项写进 `uncertainty`，不生成精密分数。

## 6. Summarize：写成 Brief

每条 Brief 包含以下可阅读结构：

**标题**：直接说清变化或用途，不夸大。

**发生了什么（What happened）**：用简短文字交代已核实事实。工具、教程和方法类内容可写它提供什么、能做什么。

**为什么值得关注（Why it matters）**：明确重要性或实用性、受影响的人和适用场景。不用“推动行业发展”等空话代替解释。

**Less 怎么看（Our take）**：仅在有帮助时提供判断、联系或推断，说明依据及边界。没有额外洞察时留空，不强写趋势。

**来源与限制**：列出具体原文链接、日期和必要的不确定性。不同主张来自不同页面时，正文应能分清对应来源。

默认使用简洁中文，保留有辨识价值的英文名称。信息足够即止，不为固定字数扩写，也不为简短省略关键条件。

## 7. 统一输出约定

以下模板是与软件层衔接的轻量内容约定，不要求特定数据库或工具。花括号内容需要替换；不得把占位内容当作真实 Brief。

```yaml
id: "{稳定标识}"
title: "{准确标题}"
published_at: null
topics:
  - "{主题}"
important: true
useful: false
confidence: "high"
sources:
  - name: "{来源名称}"
    url: "{具体原文链接}"
    type: "{official_docs / release / paper / blog / media / other}"
    primary: true
    published_at: null
what_happened: "{已核实事实}"
why_it_matters: "{重要性或用途及适用对象}"
our_take: null
uncertainty: null
```

- `important` 和 `useful` 根据内容填写，至少一项为 `true`，两项也可以同时为真。
- `sources` 至少包含一个实际支撑核心内容的具体链接。`primary` 表示是否为原始来源，不表示它天然客观或已经独立验证。
- 顶层 `published_at` 使用主要来源的发布时间；各来源可分别记录日期。只有日期时使用 `YYYY-MM-DD`，有可靠时间时使用带时区的 ISO 8601；未知填 `null`，不以运行日期补造。
- `id` 在内容保留和更新时保持稳定；已有内容的更正应沿用原标识。
- `our_take`、`uncertainty` 无内容时填 `null`。已知限制必须写明，不能以空值掩盖。
- 正式保存端补充 `created_at`。事件时间、更新日期、实体标签等仅在确有需要时增加，与架构文档保持一致。

最终交付可以是一组 Markdown Brief 或结构化记录，但字段含义保持一致。已核验且值得保留的内容与低把握待核验草稿分开交付，避免误收录。

## 8. 完成一次任务

交付前做一次简短检查：内容是否有价值，核心事实是否有依据，是否重复，标题是否准确，判断是否与事实分开，链接和时间是否真实，限制是否说明。

这是 Agent 的工作检查，不是要求用户操作的 Quality Gate。可随结果附一段任务说明，写明实际检查的范围、访问限制和是否存在待核验事项；无需保存逐条淘汰记录或内部推理。

人工如需介入，只应面对内容本身：保留、跳过或编辑。纠正已保留内容时更新对应 Brief，并按需要注明更正；不默认增加完整版本审批系统。

允许交付零条。用户没有授权发布或安排运行时，生成草稿不等于已经入库、发布或建立自动任务。

## 9. 维护方式

根据真实内容任务暴露的问题，调整来源、主题、筛选规则和表达方式。优先改进 Skill；只有简单工具和编辑规则持续无法解决具体问题时，才提出软件需求。

本文件承接旧编辑方法中仍然有效的部分，但不承接旧 Content Engine 的对象体系与流程。长期原则以 `00-less-principles.md` 为准，产品职责以 `01-less-lite-architecture.md` 为准。
