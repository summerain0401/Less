# Less · 轻量架构

状态：当前项目基线  
更新：2026-09-23
相关：`00-less-principles.md`、`02-content-skill.md`

## 1. 架构边界

Less 由内容能力与软件产品两部分构成。内容能力交付标准化 Brief，软件让这些内容可阅读、可积累、可检索、可连接。

```text
原始来源 / Web / RSS / GitHub / 博客 / 社区线索
                         ↓
                Content Skill / Agent
         Find → Filter → Verify → Summarize
                         ↓
                  标准化 Brief 草稿
                         ↓
                 按需保留 / 跳过 / 编辑
                         ↓
                  Less Content Store
               Brief / Topic / Source / 时间
                         ↓
                   Less 产品层
            Today → Topics → 按需增加其他能力
                         Ask / Signal / Timeline
```

图示是职责划分，不要求把每一层做成独立服务，也不是需要逐项实现的流水线。

## 2. Content Skill / Agent 的职责

负责搜索、阅读、价值判断、来源核验、去重与提炼。可调用现有搜索、浏览器、RSS、仓库接口或正文提取工具，按任务需要选择获取方式。

编辑规则放在 Skill 中。观察范围与来源角色沿用原产品蓝图的 Coverage Map / Source Map，见 `02-content-skill.md`；来源列表保持轻量配置，发现与筛选过程可在一次任务内完成，不默认持久化为候选库、事件库或审核队列。

内容获取不再产品化为完整采集系统。必要的小工具可以复用或编写，但不以此重建 Collector、Normalize、Event、Evidence、Value Gate、Quality Gate 的完整链路。

## 3. 最小内容模型

以下是逻辑约定，不是已经确定的数据库 schema。实现时选择足够简单的 Markdown、JSON 或轻量数据库即可；不同时维护多套权威内容存储。

### Brief：值得留下的内容单位

Brief 保存已筛选内容的事实、价值和来源。Skill 输出的草稿与正式保留的 Brief 使用同一内容结构，不另建 Candidate 业务对象。

| 字段 | 含义 |
| --- | --- |
| `id` | 稳定标识，用于引用、更新与避免重复 |
| `title` | 准确、简短的标题 |
| `published_at` | 主要来源的发布时间；未知则明确为空 |
| `what_happened` | 可独立读懂的事实经过与具体变化；方法类内容写清做法、结果和适用条件 |
| `why_it_matters` | 为什么重要或有用，适用于谁 |
| `our_take` | 明确标为判断的 Less 观点；无必要时为空 |
| `sources` | 来源列表，保留名称、具体原文链接与类型 |
| `topics` | 少量主题标签 |
| `important` / `useful` | 布尔判断，至少一项为真，无需分数 |
| `confidence` | 对核心事实的核验把握，取 high / medium / low |
| `uncertainty` | 尚未确认的条件或局限；没有则为空 |
| `created_at` | 正式保留进内容库的时间，由保存端记录 |

`confidence` 是简明说明，不是来源评级或产品评分体系。低把握草稿不直接作为确定事实进入 Today。

仅在需要时增加 `event_at`（事件发生时间）、`updated_at`（更正时间）、`entities`（公司、人物、产品名称）等字段。实体先用标签，不要求独立 Entity 系统。

多来源直接使用 `sources` 数组，并标明主要来源。原文发布时间、事件时间和入库时间不可混用；具体格式见内容 Skill。

### Topic：组织和探索内容

最初只需名称、稳定标识及可选的一句说明。一个 Brief 可以属于多个 Topic。

AI Coding、Agents、Reasoning、Open Source 等可作为起始示例，实际主题由收录内容决定，不预建庞大的分类树。

### Source：来源信息

只需名称、地址、类型，可选关注主题与备注。可用配置文件维护，无需 Source Registry 后台。

Source 配置中的地址用于发现内容；Brief 中的链接应指向支撑该条内容的具体页面。来源名称相同，不能替代具体引用。

## 4. 最小产品闭环

首要目标是完成：**Skill 交付少量 Brief → 保留内容 → Today 阅读 → 打开详情与原始来源。**

初期人工操作可通过文件或简单界面完成，主要是保留、跳过、编辑。Review 页面不是启动前提，也不发展为多阶段编辑审批流。正式内容库只保存保留结果；未保留草稿无需进入长期业务模型。

Today 优先展示当天选入的少量内容，并显示来源日期，避免把较早的资料误称为当天新闻。没有合适内容时允许为空，不为凑数降低标准。

内容卡片突出标题、事实要点与价值说明；详情展示完整的 `what_happened`，并补充判断、限制和原始来源。首轮验证关注读起来是否轻松、内容是否可信、保留是否方便。

## 5. 产品如何自然生长

以下是演进方向，不是同一版本的交付清单，也不绑定旧的周计划。

| 能力 | 解决的问题 | 何时值得增加 |
| --- | --- | --- |
| Today / Brief 详情 | 今天有什么值得知道，依据是什么 | 第一优先级，先跑通真实阅读 |
| Topics | 我关心的领域最近有什么变化 | 已有内容需要按主题回看时；先做简单分组 |
| Ask | 基于 Less 已保留内容回答问题 | 内容库已有可检索积累，且出现真实提问需求时 |
| Signal | 多条 Brief 共同呈现什么变化 | 跨条目联系反复出现，且整理它确实有价值时 |
| Timeline / Digest | 回顾变化过程或阶段重点 | 出现具体回顾需求时，从已有 Brief 派生 |

**Ask** 优先检索内容库，回答附相关 Brief 与来源。库内依据不足时明确说明；如需外部搜索，由内容能力补充，并标明新取得的信息。不默认建设知识图谱或复杂检索基础设施。

**Signal** 起初可以是一段判断加关联 Brief：观察到什么、为什么这样判断、什么可能改变判断。它是可修正的综合观点，不是事实标签。无需先建 Thesis 状态机、Evidence 表、复评流程或自动关联系统。

## 6. 明确不在当前范围

- 完整采集平台、来源健康管理、全量原文仓库及覆盖率体系。
- Item → Event → Evidence → Candidate → Brief 的强制业务链。
- Important / Useful 分数、Value Gate / Quality Gate 后台。
- 多层审核、复杂 Signal 状态流、研究机构式证据工作台。
- 为未来可能使用而预建的知识图谱、多服务架构和大规模指标系统。

必要的输入格式检查、保存失败提示和少量运行记录可以存在，但不扩大为新的业务系统。核验与去重仍要完成，只是不把每个编辑动作都产品化。

## 7. 旧项目与复用

旧系统定位为 **Less Content Engine Prototype — Archived**。保留其历史，不再按原路线继续加功能。

迁移时可通过 Git tag 或归档分支保存旧版本，再从干净的新分支推进轻架构；具体分支名和执行方式由实际仓库确定。本文件不表示归档或迁移已经完成。

按需复用 Today、Brief 展示、通用 UI、正文提取、Prompt 和来源配置。数据库从最小需要重新选择结构，不整体复制旧 schema。每项复用都应服务于当前闭环，而不是要求新产品兼容旧工作流。
