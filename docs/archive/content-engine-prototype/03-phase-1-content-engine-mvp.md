## 1. 首期要证明的事情

**验证能否持续、稳定地从庞杂 AI 信息中，每天筛选出约 3–5 条我们自己都愿意看的高质量内容，并逐步形成可验证的 Signal。**

第一期交付一套可每日使用的内部内容系统。它需要能发现、筛选、核验、编辑、回溯和连接。漂亮网站、用户增长和商业收入不作为本阶段成功标准。

核心假设有三个：少量优质来源足以支撑有价值的候选；机器辅助后，人工能以可持续成本产出 Brief；跨时间的证据记录能形成超出每日摘要的理解，并允许否定自己的判断。

3–5 条是验证目标，不是最低配额。低产日不填充；若长期不足，要分析来源、流程或价值假设，并如实报告验证尚未通过。

本计划中的样本量、百分比和耗时阈值是为首轮运行提出的**暂定验收目标**，不是历史对话已经实测的结果。Week 1 结束时结合基线确认；变更要记录原因与生效日期，不能在验收后降低门槛来宣称成功。

## 2. 范围与交付边界

### 必须跑通的闭环

**10–20 个 Source → Collector → Raw Item → LLM Normalize → Event → Candidate / Value Gate → Quality Gate → Editorial Inbox → 人工 Review → Brief / Evidence → 一个 Signal。**

| 模块 | Phase 1 的最低能力 |
|---|---|
| Source Registry | 登记具体节点、角色、Topic 权威依据、访问方式、状态和质量反馈 |
| Collector | 先实现少量容易维护的来源接口；定时获取、重试、去重、保存失败原因 |
| Raw Item | 保留原始材料、URL、来源、作者、发布时间、抓取时间、内容版本 |
| LLM Normalize | 摘要、陈述提取、Fact 候选 / Claim 区分、Entity、Topic、原文定位；输出可人工检查 |
| Event | 去重聚类建议、关联 Items、人工合并/拆分和历史记录 |
| Candidate Selection | Important × Useful 双维理由，以 Important OR Useful 准入；可解释排序 |
| Quality Gate | 关键陈述与 Evidence 映射；通过 / 待核实 / 不通过；原文核对和人工确认 |
| Editorial Inbox | 候选、原文、证据缺口、草稿、状态与审核动作集中呈现 |
| Brief / Evidence | 草稿、审核、批准、内部发布、更正及来源回溯 |
| Signal | 选择 AI Coding / Agentic Software Engineering；维护 Thesis、正反证据、Timeline、状态与 Our View |
| 运行记录 | 每日漏斗、错误、耗时、成本、漏选抽查、来源健康和编辑反馈 |

第一版至少具备人工证据核查；自动检索可逐步补充，不能把 Quality Gate 延后到下一期。Signal 的匹配、反证查找和状态管理可以先由人完成，无需开发自主发现趋势的复杂 Agent。

### 首期明确不做

Native App、复杂 Web 前台、用户体系、付费、复杂推荐算法、几百个 Sources、全自动发布、复杂知识图谱、多渠道自动分发，以及为了覆盖所有媒介而一次性建设全部采集器。

允许简单内部网页作为 Inbox、可阅读的 Today 列表或 Markdown 导出。内部访问限制与必要凭据保护属于基本运行保障，不意味着建设面向公众的账号体系。首期只供内部审阅，不默认对外发送邮件或发布社交内容。

## 3. Week 1：Source Registry + 最小采集管道

**目标：**每天能稳定拿到可回溯的原始材料，并看到结构化结果；建立手工筛选的耗时与质量基线。

### 具体任务

1. 确定首批约 10–20 个具体 Source 节点，优先满足 AI Coding / Agents 的连续观察，同时保留少量 Frontier、Voices 和独立视角。按“如果只能看这些，是否仍有价值”筛选。
2. 逐个确认原始内容地址、访问可用性、可获取字段与更新节奏；区分公司主页、内容节点和实际采集入口。首轮优先可稳定获取的 Feed、发布记录或文档页面，复杂平台暂用人工补录。
3. 建立 Registry 与最小 Collector；原始材料先保存，再 Normalize。支持重复运行不重复造 Item，失败可重试，无新内容与获取失败分别记录。
4. 将 LLM 任务限制为提取与分类：摘要、陈述、Entity、Topic、日期、原文位置。无法获得的字段保留未知，记录模型/提示版本与失败。
5. 用至少两次独立手工筛选记录基线耗时、来源数、原始阅读量、候选和最终入选理由；同时开始形成供 Week 2 使用的小型人工标注样本。
6. 确定每日观察截止时间、审核节奏、负责人、运行记录位置和首期运行成本预算。首期可一人兼任，不预设已经有团队。

### Source Registry 最小字段

| 字段组 | 要记录的内容 |
|---|---|
| 身份 | Source ID、名称、具体节点、所属主体、原始地址、采集入口 |
| 编辑角色 | Primary / People / Builders / Intelligence / Discovery 主要角色，必要时附次要角色 |
| 专长 | Topics、Coverage、Source × Topic Authority 的理由、信息偏向或利益关联 |
| 接入 | 获取方式、计划频率、最近成功时间、Active / Paused / Needs Review、失败原因 |
| 反馈 | 采集量、有效候选、入选内容、失真或更正、人工维护时间、最后复核日期 |

可先以 12 个节点做容量草案：6 个发布/研究等 Primary 节点、3 个工程实践节点、1 个人物节点、1 个独立分析节点、1 个 Discovery 节点。此分配只是起步检查表；角色允许交叉，不为凑齐类别保留低质量 Source。至少保留不同组织和独立视角，避免所有证据最终来自同一个厂商。

人工补录材料应标注获取方式与缺口；未自动接入的来源不能计为自动采集成功。若某节点长期不可用，可替换，但记录替换原因和前后覆盖差异。

### 交付物

- 可编辑 Registry，含 10–20 个已核验节点及接入状态。
- 可重复运行的最小采集与 Normalize 流程；Raw / Normalized Item 可对照查看。
- 来源健康记录、失败重试记录、手工基线和首批标注样本。
- Week 1 决策记录：实际启用来源、观察节奏、成本预算及指标基线。

### 验收标准与指标

- [ ] 至少 10 个节点完成实际接入；需人工补录的其余节点单独列出，不能用“已登记”冒充接入。
- [ ] 连续 3 天运行；计划采集成功率暂定 ≥95%，无新内容的成功检查可计成功，解析失败不可计成功。
- [ ] 重跑同一批材料不新增重复 Item；更新内容保留版本差异。
- [ ] 抽查至少 30 个不同来源 Items，数量不足则全查并记录样本不足；关键字段正确率暂定 ≥95%。
- [ ] 每个抽查 Item 均能回到原始地址/保存版本；Normalize 没有凭空新增原文不存在的关键主张。
- [ ] 完成至少两次手工筛选的时间记录，便于后续比较；尚未证明节时也如实保留。

低频 Source 三天没有新内容时，以明确标记的历史材料回放验证采集能力，但不把回放算作当日新内容产出。

## 4. Week 2：Event、筛选与 Editorial Inbox

**目标：**把材料整理成可审核的 Event 候选，编辑能够看到入选原因与证据缺口。

### 具体任务

1. 实现 Event 骨架与聚类建议：主体、动作、对象、时间、版本、引用关系和语义相似性共同参与。加入人工合并、拆分与恢复关联的能力。
2. 实现 Important / Useful 两条理由、Value Gate 状态和排序；Candidate 初筛与显式 Value Gate 可复用结果。两个都弱时退出，不把缺证据者自动当低价值者。
3. 实现最小 Quality Gate：列出关键陈述、原始出处、Supporting / Counter / Context 关系、核验状态与待办。允许人工补证。
4. 搭建简单 Inbox：看 Event 与 Items、看双维理由、看原文和缺口、编辑判断、通过/暂缓/驳回/仅存证、纠正聚类。操作留下人和时间。
5. 用人工标注样本比较机器结果；样本覆盖同源转载、跨语言复述、相似产品的不同发布、观点与事实、Useful 强但 Important 弱等边界。
6. 保留对机器驳回项的抽查，避免只看候选池而不知道漏掉了什么。

### 交付物

- Event 与 Item 关联、聚类纠正记录。
- 可解释 Candidate Selection、两道门的状态与 Evidence 记录。
- 可完成基本编辑动作的 Inbox。
- 至少 30 组人工标注的同事件/不同事件材料对，以及候选筛选评估记录；样本不足时显式标明。

### 验收标准与指标

- [ ] 至少 3 次日常运行，能把当日材料压缩成可处理队列；约 10–20 个 Candidate 是容量参考，不是固定输出数。
- [ ] 聚类样本上的错合与错拆分别报告，合计错误率暂定 ≤10%；不能只看“去重后数量减少”。
- [ ] 抽查候选的 Value Gate 理由，人工认可率暂定 ≥70%；核查至少 20 个机器排除的 Events，检查价值漏选。
- [ ] 每个候选显示 Quality Gate 状态、关键证据或明确缺口，不允许默认全部通过。
- [ ] 待核实内容无法直接进入 Published；合并/拆分后 Brief 与 Evidence 关联仍正确。
- [ ] 编辑能在 Inbox 内完成从看理由到查看原文、作出决定的过程；记录总耗时和操作卡点。

## 5. Week 3–4：真正生产与第一个 Signal

### Week 3：人工 Review → Brief → Evidence

**目标：**连续产出可以实际阅读的内部 Today，并检验其质量与人工成本。

**具体任务：**

1. 按[手册第 6 节](02-editorial-handbook.md#6-brief-的写法与交付模板)生成 Brief 草稿，维护 What happened / Why it matters / What changed / Our take / Sources，Useful 内容按需添加 Try it。
2. 实现 Draft → In Review → Approved → Published；Published 为内部可读状态。未明确人工批准不能发布；修改已批准核心内容需重新审核。
3. 关键事实关联 Evidence 与原文位置，Fact / Claim / Interpretation 分开；保存审核记录、修改版本和更正路径。
4. 连续运行至少 5 个编辑日，记录入选数量、低产原因、漏选、编辑时间和阅读反馈。每天产生有限 Today，而非不加选择地列出所有已核验候选。
5. 为 AI Coding 建立首个 Signal Candidate，开始整理当前及必要历史材料；提前安排反证检索，避免把 Week 4 全耗在补原始证据。

**交付物：**至少 5 个编辑日的 Today 记录、已审核 Briefs 与 Evidence、每日耗时与反馈、一次更正演练、首个 Signal Candidate。演练可用独立的测试记录，不能混入真实内容或污染事实库。

**验收标准与验证指标：**

- [ ] 每条内部发布 Brief 均有人工批准、具体价值理由、关键事实证据和原文定位。
- [ ] 未批准发布为 0；发布前发现的关键事实错误全部修正；发布后发现的错误逐项更正并追踪关联影响。
- [ ] 项目负责人在次日阅读已发布内容，分别记录“仍愿意看”与原因；暂定比例 ≥80%，不是以“自己写过”默认通过。
- [ ] 记录人工采集补录、审核、写作、事实核查、Signal 工作和故障处理的总时间，不能只计点击发布耗时。
- [ ] 完成一次可回溯更正：修改 Brief 后，相关 Evidence / Event / Signal 的受影响状态可定位。

### Week 4：Signal + 连续运行验收

**目标：**跑通一个可验证也可被推翻的判断，并据实际运行决定是否进入下一阶段。

**具体任务：**

1. 在 Agentic Software Engineering / AI Coding 中明确一个 Thesis、适用范围、观察期与否定条件。默认以“部分有清晰边界的软件工程任务开始从逐步提示转为任务委派与人工验收”作为待检验方向，可按证据收窄。
2. 关联不同 Events 的 Supporting Evidence 与 Counter Evidence，逐条检查独立性；历史补录标原始发生日期与本次加入日期。
3. 主动查失败实践、Review 成本、真实采用、效果边界与替代解释。产品推出、真实使用、业务收益分别证明不同层面的事情。
4. 建立 Timeline，完成至少两次有记录的人工复评：起始判断与加入新材料后的判断。状态可以保持 Candidate、Emerging，也可以 Weakening / Rejected，不为交付而升到 Strong。
5. 形成连续 7 个自然日的真实运行窗口，可从 Week 3 延续；无合格内容的日期也保留记录。回放不能代替这段稳定性观察。
6. 汇总质量、漏选、耗时、成本与内容反馈，写一页阶段结论：通过、部分通过需继续验证，或核心假设暂不成立。

**交付物：**一份可阅读的 Signal 工作记录，包含 Thesis / Status / Supporting Evidence / Counter Evidence / Timeline / Our View / Last Updated；7 天运行数据；来源保留/替换建议；阶段复盘和后续范围建议。

**验收标准与验证指标：**

- [ ] 至少一个 Signal 完整可回溯；每条 Evidence 能指向原始材料并解释支持或反驳哪一部分。
- [ ] 至少两轮人工复评记录；必须能说明新材料使判断维持、收窄、增强或减弱的理由。
- [ ] Counter Evidence 包含实际找到的相关反面/限制材料；若确未找到，保留检索日志、证据缺口，阶段结论明确“反证覆盖未充分验证”。不得编造反证。
- [ ] 用清楚标注的测试记录验证 Weakening / Rejected 状态变更与历史保留；真实 Signal 仅按真实证据变更。
- [ ] 完成第 6 节指标复核；对来源故障、低产日、未解决的证据缺口和超预算如实说明。
- [ ] 项目负责人决定是否继续。只完成软件流程，不自动等于证明内容假设。

若压缩为 3 周，可把 Week 4 的 Signal 工作前移到 Week 3，并复用 Week 2–3 已合格运行记录形成连续窗口；不能取消反证、人工核验或 7 天观察。不满足条件时按 4 周执行，必要时记录延期原因。

## 6. 验证指标与结束条件

### 指标口径

每日报表至少保留：日期/截止时间、计划与成功采集次数、Raw Items、去重后 Events、Candidates、Value Gate 通过数、Quality Gate 通过/待核实/不通过数、人工入选数、Published Briefs、仅存证数、错误、时间与成本。不要把不同层级的数直接相减当“过滤率”。

| 指标 | 计算 / 检查方法 | 首轮暂定目标 |
|---|---|---|
| 采集成功率 | 成功获取并完成必要解析的计划任务 ÷ 应执行任务；重试不增加分母，漏执行算失败 | 连续窗口 ≥95% |
| Normalize 关键字段准确率 | 人工核查正确的关键字段 ÷ 被核查字段；原文缺失且正确标未知算正确；无依据填值算错误 | ≥95%；新增虚构关键主张逐项修正 |
| 聚类错误率 | 人工标注材料对中，错合或错拆对数 ÷ 检查对数；两类分开报告 | 合计 ≤10% |
| 候选价值认可率 | 编辑认为通过 Value Gate 的 Candidates ÷ 已复核 Candidates | ≥70%，不与最终发布率混同 |
| 漏选审计 | 对排除 Events 随机抽样，人工盲判是否具备价值；另查已知重要事件是否缺失于源头 | 每周至少 20 个或不足时全查；严重漏选必须分析 |
| 发布可追溯率 | 有关键陈述—Evidence—原文完整对应及人工批准的 Briefs ÷ Published Briefs | 100% |
| 实际阅读价值 | 次日仍愿意读的 Briefs ÷ 已复读 Briefs；附具体原因 | ≥80%；首期只代表内部用户 |
| 内容稳定性 | 7 天中，质量门槛通过且自然产生约 3–5 条值得读内容的天数 | 暂定至少 5 天；其他天记录原因，不填充 |
| 人工负担 | 所有必要人工时间总和，包括反证工作与故障恢复；另列非重复的一次性开发/设置时间 | 暂定日均 ≤60 分钟，且较手工基线下降 ≥30% |
| 运行成本 | 抓取、模型及其他实际增量成本；按日及每篇已批准 Brief 记录 | 不超过 Week 1 设定预算；没有 Brief 时不计算单篇成本 |
| Signal 可检验性 | Thesis 边界、正反证据、独立性、两轮复评、Timeline、可解释的状态决定 | 全部可检查，成熟度高低不作成功指标 |

样本小不宣称统计结论。漏选抽样不能估计整个互联网的召回率；低频来源健康不能证明全行业覆盖。手工基线与系统运行必须尽量采用相近来源范围和质量要求，范围不同则只作参考，不宣称精确节时。

“严重漏选”指会改变当天核心理解或错过读者必要行动的信息，由编辑说明影响和漏失环节；不能单凭模型分数定义。规则调试样本与最终验收样本尽量分开，避免只记住曾经见过的案例。

### 阶段结论

**通过：**关键流程可用、发布门槛满足、连续观察支持内容稳定性与人工成本目标，且首个 Signal 展示了可追溯、可修正的判断。此时才讨论最小对外 Surface。

**部分通过：**流程已跑通，但供给、节时、来源覆盖或反证验证不足。明确哪项尚未成立，只延长对应验证或修复瓶颈；保持质量门槛。

**暂不成立：**内容长期无法产生足够价值，或人工成本未下降且难以持续，或 Signal 只是重复新闻标题。回到来源与编辑假设，避免继续堆功能。

即使技术和指标通过，也只证明初步内部价值；外部用户需求、留存和商业化尚需独立验证。

## 7. 技术实现原则

第一版可用关系型数据库，例如 PostgreSQL 加必要的向量能力。Source / Item / Event / Brief / Signal / Entity / Topic / Evidence 及关联关系先表达清楚，不提前锁死数据库、框架、模型供应商或部署方式。

向量相似度用于召回可能相关材料，不直接决定“同一事件”“证据真实”或“Signal 成立”。先使用简单、可检查的规则与人工纠正；只有明确瓶颈出现时再增加复杂度。

多个职责明确的小 LLM 任务更适合首期：提取、分类、聚类建议、价值评估、证据检索、Brief 草稿、Signal 匹配。每个任务有固定输入、结构化输出、原文引用、错误状态和模型/提示版本。可以顺序执行，不要求多 Agent 架构或自主规划。

原始材料、模型输出与人工批准结果分别保存；重跑模型不能覆盖人工审定字段。保留稳定 ID、版本、关联和决定日志，方便更正与回溯。错误能重试，重复处理不重复生成已存在对象。

把外部文章、仓库内容与模型读到的文字当作待分析数据，不允许其改写筛选规则、跳过审核或触发执行。系统只授予完成采集与编辑所需能力；发布与 Signal 状态变化由明确人工动作触发。

优先保证“哪里错了能看见、结果能纠正、来源能回溯”。界面精致程度和系统组件数量不作为工程成果。

## 8. 关键风险与验证方式

| 风险 | 可观察的失败 | 验证方式 | 首期应对 |
|---|---|---|---|
| 低质量采集 | 大量导航、广告、残缺正文或重复材料 | 随机对照原始页面；每 Source 看有效材料与维护时间 | 修解析、暂停低质节点；区分无更新与失败 |
| AI 误判 | 把宣传当事实、误删 Useful、推断超出原文 | 人工盲标、关键陈述核查、排除项抽样 | 提示任务收窄；保留不确定状态；人工批准 |
| Event 聚类错误 | 同事件多次占位，或不同事件被合并 | 同/不同事件对测试、查看被合并 Items | 加版本/时间/动作信息，允许拆分并复查关联 |
| Source 失真 | 官方口径被当独立验证、断章取义、转述层层放大 | 追原文和引用链，核对全文语境及更正 | 按主张判断 Primary；保留来源根和限制 |
| 来源结构偏差 | 只看厂商发布，忽视独立实践与失败 | 看来源根分布、漏选与反证覆盖 | 增补独立节点，避免以数量制造多样性 |
| Signal 确认偏误 | 支持材料很多，Counter 永远为空 | 查看反证查询、替代解释及两轮复评差异 | 每轮主动搜反证；保持/降级也是正常结果 |
| 人工负担过高 | 每天反复查同样材料、候选堆积、审核草率 | 分步骤计时，看中位数与峰值，并记录积压 | 缩小来源与候选范围，改善原文定位和证据展示 |
| 为凑条数降质 | 低产日充满低价值工具更新 | 审计边缘入选理由和次日愿读率 | 允许少发或不发；单独分析持续供给不足 |
| 内容过时或更正遗漏 | Brief 已改，Signal 仍引用旧证据 | 更正演练与关联回溯 | 版本化并标出受影响对象，人工复核 |
| 运行与成本失控 | 失败重试无界、重复调用、漏执行 | 每日任务日志、重试与成本检查 | 限制重试与调用预算；保留人工恢复路径 |

## 9. 工作记录与维护方式

运行后，将 Registry、标注样本、每日结果、Signal 和复盘放在同一个 Less 项目目录或正式开发仓库中。以下是建议的后续位置，尚未生成实际数据：

| 建议位置 | 用途 |
|---|---|
| `operations/source-registry.*` | 来源实际登记与健康信息，格式随实现选择 |
| `operations/daily/YYYY-MM-DD.md` | 每日漏斗、阅读结果、耗时、错误与待办 |
| `operations/signals/<signal-id>.md` | 首个 Signal 的可读记录或数据库导出 |
| `operations/reviews/` | 每周复盘、样本与阶段结论 |

数据库可作为业务记录主存储，可读导出用于复盘；不要同时人工维护互相漂移的两份真值。每日记录至少包含日期/窗口、来源异常、入选与未入选原因、Brief IDs、Signal 变动、编辑时间、成本、错误和下一次待办。

每周结束由编辑负责人确认内容问题，实施负责人确认管道问题，项目负责人确认范围变化；同一人兼任时分别回答这三类问题即可。调整指标前写明原目标、新目标、原因、证据和生效日期。
