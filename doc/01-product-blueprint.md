## 1. 为什么做 Less

Less 来自一个真实的个人需求：发起者高度关注 AI，长期阅读产品发布、工程实践、人物观点和行业进展，却越来越难以用合理的时间完成筛选。信息分散在实验室博客、论文、代码仓库、社交平台、视频、播客与媒体中。同一件事被反复转述，事实、宣传与判断混在一起；真正有价值的内容又未必最热门。

用户的困难不只是“看不完”。他还需要判断原始出处、辨别重复信息、理解变化的意义，并记住它与过去发生的事情有什么关系。这些工作每天重来，时间和注意力被反复消耗。

Less 首先服务发起者自己，以及同样深度关注 AI、已经感到信息过载的人。开发者、产品经理、创业者、科技从业者和深度 AI 用户可能有共同需求，但第一阶段不预设已验证的广泛用户画像、地区覆盖或商业模式。

第一位用户应能回答三个问题：今天什么值得知道？哪些东西值得实际尝试？最近的零散变化共同说明了什么？如果自己都不愿持续阅读，系统还没有证明价值。

## 2. 品牌与产品定义

| 层次 | 固定表达 |
|---|---|
| Brand | Less |
| Slogan | Read less. Know more. |
| 内部产品原则 | Less noise. More signal. |
| 中文核心价值 | 我们不希望你看得更多，而是希望你看得更少，但知道得更多。 |

中文直接使用 Less，不另设中文品牌名。AI Daily 是历史项目代号。品牌语气保持克制、可信、冷静、有判断力；少用夸张修辞，明确交代证据与不确定性。

**Less 是一套 AI 行业 Intelligence System：持续发现真正重要或有用的信息，验证事实，提炼和解释变化，并将它们连接成可以不断修正的行业认知。**

它不是以新闻数量、更新速度或无限信息流为核心的传统 AI 新闻网站。其核心产品是 Content / Intelligence Engine；文中“内容引擎”和“Intelligence Engine”指同一套发现、筛选、验证、编辑和连接能力，不代表需要开发两套系统。

### 三层产品结构

| 层次 | 责任 | 长期积累 |
|---|---|---|
| Intelligence Engine | 判断哪些信息值得进入、哪些事实可核查、哪些连接有意义 | 来源体系、编辑方法、运行反馈 |
| Content System | 保存来源、材料、事件、内容、证据与可修正的判断 | 结构化内容资产及其历史 |
| Distribution Surfaces | 根据使用场景组织、呈现和送达内容 | 用户触达与阅读体验 |

Web、Newsletter、App、Social、Conversation、API 都是 Distribution Surfaces。它们可以共享同一份事实、证据与编辑判断，再调整长度和表达。不能为了渠道重写出彼此矛盾的核心事实，也不能把一个渠道的页面结构变成整个数据模型。

Today 回答“今天值得知道什么”，Signals 回答“哪些变化值得持续观察”。这是两个阅读时间尺度，不是首期必须上线的两个公开页面。用户应能在有限阅读后停下来；深入理解时，再沿证据、事件和时间线展开。

## 3. Less 提供什么价值

价值链为：**发现 → 筛选 → 提炼 → 解释 → 连接**。

发现让重要材料被看见；筛选减少注意力支出；提炼保留核心事实与必要语境；解释回答变化的意义；连接让今天的信息成为明天理解行业的证据。

“少”不是缩短字数的比赛。删掉必要条件、限制或反证，会使内容更短却更不可信。Less 要减少的是重复、低价值材料和用户自行核查的负担，同时提供足够清楚的出处，让读者可以深入。

产品取舍遵循以下基线：

- 重要性与实际价值优先于热度、发布时间和转发量。
- 每条内容都要说明为什么值得占用注意力。
- 不为日更、栏目配额或固定条数降低标准。
- 判断可被修正；保留当时依据与后续变化。
- 信息能够复用和连接，而非发布后成为孤立旧文章。

每天 3–5 条是 Phase 1 的验证目标与有限阅读形态，不是最低生产配额。只有 3 条就发 3 条；不足 3 条也如实记录；没有合格内容可以不发。超过 5 条确有必要时，可由编辑记录理由。具体运行方式见[编辑手册第 8 节](02-editorial-handbook.md#8-每日运行与人工-review)。

## 4. Selection Framework：两道门与编辑判断

| 环节 | 核心问题 | 结果 |
|---|---|---|
| Value Gate | 足够 Important，或者足够 Useful 吗？ | 通过、待判断、淘汰 |
| Quality Gate | 支撑关键事实和判断的来源与证据够不够？ | 通过、待核实、不通过 |
| Editorial Judgment | 变化是什么，意义是什么，值得怎样表达和连接？ | 成为 Brief、仅存证、继续观察、放弃 |

**Important OR Useful** 是准入逻辑。历史讨论中的 Important × Useful 表示两个观察维度，既不是分数相乘，也不是两项必须同时满足。

Important 帮助用户理解 AI 正在往哪里走，包括能力、技术路线、成本结构、行业格局或组织方式的实质变化。Useful 帮助用户更好地构建或使用 AI，包括有适用条件、可检验且值得复用的实践。两者兼具可以优先，但其中一项很强、另一项很弱，也可以通过 Value Gate。

Source / Evidence 是独立质量门槛。再高的价值判断都不能抵消关键证据缺失。模型的分数、来源的名气以及多个网站重复报道，都不能自动证明事实。

通过门槛后，编辑回答四个问题：

| 维度 | 要形成的判断 |
|---|---|
| Change | 与哪个已知基线相比，能力、实践、成本或认知实际改变了什么？ |
| Signal | 这是否支持、限制或反驳一个更大变化的判断？也允许暂时无关。 |
| Half-life | 一周、三个月后还剩下什么价值？哪些条件会使它过时？ |
| So What | 用户读完多理解了什么，或能更好地做什么？ |

这些问题帮助判断，不要求每条内容四项全满。Useful 实践可以没有行业级 Signal；短期信息也可能因为紧迫而重要。不能为了符合表格，给小更新强行包装趋势。

## 5. Coverage Map：我们观察什么

Coverage 是编辑观察视角，不等同于前台栏目，也不同于 Topic。

| 核心 Coverage | 观察问题 | 典型进入理由 |
|---|---|---|
| Frontier | AI 的能力边界和行业方向改变了什么？ | 模型、推理、多模态、Agent、开源或基础设施的实质进展 |
| Builders | 人们如何真正构建和使用 AI？ | 工程方法、AI Coding、Context / Memory、工具调用、工作流与真实实践 |
| Voices | 影响 AI 发展的人在思考什么，其判断如何变化？ | 有实质观点和完整语境的访谈、演讲、长文、研究或发言 |
| Signals | 分散事件共同指向什么变化？ | 对跨事件、跨时间的判断持续积累正反证据 |

Business / Science / Robotics / Society 选择性覆盖，重点看是否跨过 Important 门槛。例如改变行业结构的商业动作、科研能力突破、AI 向物理世界延伸的重要进展、就业或治理的结构变化。它们不设日常填充配额；某条材料同时提供扎实工程实践时，也可按 Builders 的 Useful 路径处理。

AI Tools / Products 不作为独立 Coverage。推动能力边界的进入 Frontier，形成有用实践的进入 Builders，能够支持或反驳更大判断的连接 Signals。普通产品发布、工具榜单、融资快讯、论文流水账、跑分排名、人物八卦及泛化 Prompt 大全，默认没有独立收录理由。

Voices 关注思想而非名人动态。人物的职位和影响力不能替代观点价值；发言记录与观点是否成立需要分别核查。

## 6. Source Map：我们靠什么观察

Source Map 是分层来源体系，Source Registry 是其可运行的登记表。Source 以具体内容节点管理，可以是一家实验室的工程博客、一个仓库的 Releases、一位研究者的个人博客或某媒体的专业栏目。公司名、网站名不等于一个可采集且质量均匀的 Feed。

| 层级 | 主要作用 | 使用边界 |
|---|---|---|
| Primary | 发布、研究、代码、数据等事实源头 | 优先回溯，但官方自述仍有适用范围和利益立场 |
| People | 思想、经验与方向判断的源头 | 按 Source × Topic Authority 使用，不把人物整体权威化 |
| Builders | 实践方法、工程复盘、开源实现 | 查方法、条件、失败案例与可复现性 |
| Intelligence | 专业媒体、研究机构、独立分析的发现、调查、背景与交叉验证 | 转述需回溯；原创调查或测量可构成针对该事实的一手证据 |
| Discovery | 社区讨论、榜单、社交平台等线索入口 | Discovery ≠ Truth，热度只提示值得检查 |

层级描述来源角色，不是绝对可信度排名。同一 Source 可以有多个角色，但登记主要角色以便管理；某条具体材料是否为 Primary，需要针对它所支持的主张判断。官方视频是一次发言的一手记录，社区作者自己的复现实验也可能是某个结果的一手材料。平台名称不能直接决定证据等级。

**Source × Topic Authority** 回答：谁在什么领域、基于什么经历或材料值得优先关注？它用于检索与候选排序，不能替代本条证据核查。Registry 应保留 Topic、领域依据、来源角色、访问方式、更新节奏、质量反馈和最后复核时间。

Phase 1 只接入约 10–20 个高质量节点。具体接入地址、可用性与采集方式在 Week 1 核验；本蓝图不把对话中列举的平台当成已经接入的来源。

## 7. Content / Intelligence Engine 如何工作

**Collect → Normalize → Cluster → Candidate → Value Gate → Quality Gate → Editorial Judgment → Publish → Connect**

这是处理顺序，不要求独立部署九个服务。

| 步骤 | 输入与责任 | 必须留下的结果 |
|---|---|---|
| Collect | 从已登记 Source 获取原始材料 | Raw Item、原始地址、时间、内容版本、抓取状态 |
| Normalize | 提取摘要、陈述、Entity、Topic 和原文定位 | 结构化 Item；未验证陈述不能自动写成 Verified Facts |
| Cluster | 判断哪些材料讲同一件事 | Event 与 Item 关联、合并依据及可拆分记录 |
| Candidate | 召回可能 Important 或 Useful 的 Event | 候选理由；不确定项可保留待审 |
| Value Gate | 明确两条价值路径是否至少一条成立 | 独立的 Important / Useful 理由及决定 |
| Quality Gate | 回溯原始出处、核对关键陈述、识别冲突 | Evidence、未决问题和核验状态 |
| Editorial Judgment | 判断 Change / Signal / Half-life / So What | 选题决定、Brief 草稿或仅存证决定 |
| Publish | 人工批准后形成可使用版本 | Brief 版本、审批人、时间与发布状态 |
| Connect | 将证据、事件、内容关联到长期判断 | Signal 关联建议及人工确认的更新记录 |

Candidate 是 Event 的编辑候选状态，不是第九种核心知识对象。系统初筛和显式 Value Gate 可共享一次计算，避免重复评估。证据不足者进入待核实；低价值者退出当日队列，但保留决策记录，用于检查漏选。

Publish 在 Phase 1 指内部确认并生成可阅读版本，不意味着自动发送到外部渠道。Connect 也不以发布为前提：有价值的反证可能无需占用 Daily 的一个位置，却必须进入 Signal。

## 8. Content Model v1：事实 → 内容 → 认知

这三层分别回答：世界发生了什么？用户需要知道什么？这些事情在更长时间里意味着什么？

事实层保存原始材料和经过核查的事件；内容层形成 Brief；认知层维护 Signal。原始材料本身并不全是真实事实，Event 也可以处于待核实状态。只有通过证据核验的具体陈述，才能按已核实事实使用。

### 八个统一概念

| 对象 | 定义 | 最低信息与边界 |
|---|---|---|
| Source | 信息从哪里来 | 名称、具体节点、角色、Topics、领域依据、获取方式；不是材料本身 |
| Item | 捕获的一份原始材料 | 来源、URL、作者、发布时间、抓取时间、正文或定位、内容版本；Raw 与 Normalized 是同一材料的不同表示 |
| Event | 材料所描述的一件现实事件 | 主体、动作、对象、发生时间、事实状态、关联 Items；与编辑标题分开 |
| Brief | Less 对值得知道之事的编辑表达 | 关联 Events、事实与解读、So What、Sources、审核及版本；不是原文摘要的别名 |
| Signal | 可由持续证据验证或推翻的行业变化判断 | Thesis、状态、正反证据、时间线、当前判断、最后复评时间 |
| Entity | 涉及谁或什么 | Person / Organization / Model / Product / Technology / Project；保留统一身份和别名 |
| Topic | 内容关于什么 | 如 AI Coding、Agents、Reasoning；是观察主题，不是具体公司或产品 |
| Evidence | 某份材料如何支持、反驳或限制某个陈述/判断 | 原文定位、所针对的主张、关联 Item / Event、方向、适用条件、核验人及时间 |

Evidence 是贯穿系统的一等记录，逻辑上承载“材料与判断之间的关系”。它既不是单独一篇文章，也不是在文末堆几个链接。数据库可以将它实现为带属性的关系记录，无需引入复杂图数据库。

Entity、Topic、Coverage 的区别：一个具体 Coding 产品是 Entity，AI Coding 是 Topic，Builders 是编辑观察视角。Voices 是 Coverage / 内容视图；Person 是 Entity 的一种，不再增加 Voice 一级对象。

### Item → Event → Brief → Signal 的关系

这条路径描述从原料到理解的层次。实际关系是可连接的网络：

- 一个 Source 产生多个 Items；一个 Item 可以讨论多个 Events，关联时保留对应段落。
- 多个 Items 可以属于同一 Event；同一事件被二十家转述，仍不是二十个独立事实。
- 一个 Event 可以没有 Brief，也可以在确有新增价值时形成不同 Brief；一个 Brief 可以综合多个 Events。
- 一个 Signal 可关联多个 Events / Briefs；一个 Event 也能支持一个 Signal，同时限制另一个 Signal。
- Signal 的 Evidence 必须能回到 Item 原文。Less 自己的多个 Brief 不能被当成相互独立的外部证据。

读者可从 Signal 沿 Evidence 找到 Event、Item 与 Source；编辑也能从新 Item 查到相关历史判断。逻辑关系可以像图，第一版仍可用关系型数据库和关联表表达。

**示意，非真实新闻：**某 Coding 产品发布后台任务功能，官方发布说明、代码变更和媒体报道形成三个 Items，聚成一个发布 Event。编辑形成一条解释任务委派方式变化的 Brief。这个 Event 可为“部分软件工程任务开始被异步委派”提供证据，但不能单凭产品发布推出“企业效率普遍提高”。后者需要采用与结果层面的独立证据。

## 9. Signal：长期资产的基本单位

**Signal 是 Less 对正在发生的行业变化提出的、可被持续证据验证或推翻的判断。**

Signal 必须是能够检验的句子。“AI Coding”只是 Topic；“在某类任务和团队中，软件工程正从逐步提示转向任务委派与人工验收”才是可收窄、可观察的 Thesis。

| Signal 字段 | 维护要求 |
|---|---|
| Thesis | 判断、范围、时间尺度；说明什么观察可能推翻它 |
| Status | Candidate / Emerging / Strong / Established / Weakening / Rejected |
| Evidence / Supporting Evidence | 支持材料、支持 Thesis 的哪一部分，以及限制；两个名称指同一支持证据集合 |
| Counter Evidence | 反对或限制材料；暂未发现时保留检索范围、时间与证据缺口 |
| Timeline | 事件发生、证据加入和判断改变的时间，三者分别记录 |
| Our View | 当前综合判断、争议、仍需验证之处 |
| Last Updated | 最近一次实质复评日期，不以自动抓取时间冒充 |

通常从 Candidate → Emerging → Strong → Established 发展，但不会因时间变长或文章变多自动升级。Emerging、Strong、Established 都可以转为 Weakening 或 Rejected；关键反证也可导致直接否定。Established 只代表在声明范围内得到较充分支持，不意味着永久真理。

Rejected 保留原判断、旧证据、否定理由和时间。重新开启时记录新依据和版本，不能悄悄删除错误历史。具体准入、升级和反证复评规则由[编辑手册第 7 节](02-editorial-handbook.md#7-signal-建立与持续修正)统一维护。

现有 Signal 可以帮助发现新材料，但必须保留不依赖现有 Thesis 的扫描，并主动寻找 Counter Evidence，防止系统越运行越只会证明自己。

## 10. Human × AI 与 Editorial Inbox

**机器负责发现，人负责判断。**

程序和 AI 负责采集、解析、翻译、提取、聚类建议、候选推荐、证据检索和写作草稿。人负责价值取舍、关键证据核验、解释的边界、最终发布、Signal 状态变化与更正。AI 的“已核实”标签只是建议，不能替代证据和审核。

Editorial Inbox 是首期后台核心界面。它应让编辑在一个候选上看到：对应 Event、为什么入选、Important / Useful 理由、原始材料、事实与 Claim、证据缺口、聚类关系、Brief 草稿及 Signal 关联建议。编辑能够通过、暂缓、驳回、编辑、拆分/合并 Event、连接或移除证据，并留下理由。

一个人可以兼任编辑和审核，但每条发布、每次 Signal 升降级都必须有明确的人工作出决定；不能把“无人反对”视为批准。人工工作量也是要验证的产品成本。

## 11. 阶段边界与长期方向

Phase 1 的问题是：能否持续、稳定地从庞杂 AI 信息中，每天选出约 3–5 条自己愿意看的高质量内容，并在 AI Coding / Agentic Software Engineering 跑通一个可检验 Signal？具体周计划及指标见[MVP 文档](03-phase-1-content-engine-mvp.md)。

首期用约 10–20 个 Source、最小采集、结构化、聚类、两道门、Inbox、人工 Review、Brief 与 Evidence 完成闭环。技术保持可替换：关系型数据库可承载第一版；向量能力用于辅助召回；多个职责明确的小 LLM 任务各自留下输入输出。

Native App、复杂 Web 前台、用户体系、付费、复杂推荐、数百 Source、全自动发布和复杂知识图谱都不进入首期。长期渠道选择、商业化和地区范围在内容假设验证后再决策。

希望一年后积累的，是可追溯的 Events、Briefs、正反证据和曾经改变的判断。用户问“某种软件开发方式是如何形成的”，Less 能展示当时发生了什么、我们怎样理解、哪些证据后来支持或推翻了判断。这就是 AI 行业变化的结构化历史。
