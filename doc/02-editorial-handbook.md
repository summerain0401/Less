本手册的目标是让编辑面对同一条信息时，能说明为什么收、为什么暂缓、为什么不发。术语以[蓝图第 8 节](01-product-blueprint.md#8-content-model-v1事实--内容--认知)为准；验收数字以 MVP 为准。本文案例均为假设演练，不代表真实产品发布或已经验证的行业事实。

## 1. 编辑台上的决策顺序

**确认 Event → Value Gate → Quality Gate → Editorial Judgment → Brief Review → 内部发布 → Connect。**

Candidate 初筛可提前给出价值建议；最后通过两道门与发布仍由人确认。采集进系统不等于值得报道，写成草稿也不等于可以发布。

| 决策 | 何时使用 | 必须记录 |
|---|---|---|
| 通过 | 至少一条价值路径成立，关键证据充分，能说清 So What | 通过理由、证据、编辑与时间 |
| 待核实 | 可能有价值，但原始材料、条件或关键事实有缺口 | 缺什么、谁跟进、何时复查 |
| 仅存证 | 不值得单独占用 Daily，但对已有判断有意义 | 对应 Signal / 主张、证据方向和限制 |
| 继续观察 | 模式可能成立，当前无法形成足够明确判断 | 下一次需要观察的变化 |
| 驳回 | Important 与 Useful 都弱，或关键证据不成立 | 主要原因；保留记录用于漏选审计 |

驳回原因建议用少量稳定标签：无实质价值、重复事件、证据不成立、范围不符、解释不足。待核实与驳回必须区分；没有找到证据不等于已经证明其为假。

## 2. Value Gate：什么收，什么不收

### 两条独立的价值路径

Important：这件事是否足以改变读者对能力边界、技术路线、成本、行业结构或人机协作方式的理解？写出“改变了什么、影响谁、影响在什么范围内”。

Useful：特定读者能否据此改进一项真实工作？写出“谁、在什么条件下、能做什么、有什么收益或限制”。Useful 不限于刚发布的内容，但旧材料必须交代时效与当前适用性。

**准入 = Important 足够强 OR Useful 足够强。** Important × Useful 只是二维观察框架，不计算乘积，不要求两项同时成立。

| Important | Useful | 编辑处理 |
|---|---|---|
| 强 | 强 | 优先核查；不跳过 Quality Gate |
| 强 | 弱 | 可收，例如有证据的重大能力或行业变化 |
| 弱 | 强 | 可收，例如范围明确、可复用的工程实践 |
| 弱 | 弱 | 不收，热度不能补分 |
| 暂不确定 | 任意 | 标出缺口，进入待判断；不把不确定当成高价值 |

“强”必须有一句具体理由，不能只写“重磅”“大厂发布”“业内都在讨论”。若机器排序需要离散档位，可用强 / 中 / 弱及解释；即使以后增加数值，也不能改变 OR 和独立质量门槛。

### 收录边界

| 内容 | 可收条件 | 默认不收的情况 |
|---|---|---|
| 模型、产品或工具更新 | 可核查的能力变化，或具体工作方式得到改善 | 按钮、包装、滤镜更新；仅因新品或热榜入选 |
| 工程实践 / 开源项目 | 问题、方法、适用条件、效果与成本可说明 | Star 数、演示视频或作者口号替代效果证据 |
| 人物观点 | 原话与语境完整，观点有新增解释力或发生实质改变 | 名气、争议、日常动态、断章取义 |
| 论文 / Benchmark | 方法与限制清楚，结果改变理解或实践 | 只报分数，无可比基线，预印本被写成既定共识 |
| 商业、科学、机器人、社会变化 | 跨过 Important 门槛，能说明结构性影响 | 日常融资、人事、概念股涨跌、泛政策快讯 |
| 短期故障 / 安全事件 | 对读者有明确影响与应对价值，证据可核查 | 仅制造焦虑，或一次无长期意义的小波动 |

AI Tools / Products 按价值进入 Frontier / Builders / Signals，不建立独立 Tools 配额。也不要求每天四个 Coverage 各占一条。Coverage 的完整边界见[蓝图第 5 节](01-product-blueprint.md#5-coverage-map我们观察什么)。

## 3. Quality Gate：先明确能证明什么

### Fact / Claim / Interpretation 分开处理

| 类型 | 含义 | 编辑写法 |
|---|---|---|
| Fact | 在明确范围内已由证据核实的事实 | 直接陈述，紧邻对应来源，保留日期、版本与条件 |
| Claim | 某主体提出、其真实性尚待核实或只获局部支持的主张 | “作者称 / 公司报告 / 研究在该条件下发现”；保留归属和核验状态 |
| Interpretation | Less 基于事实与证据作出的解释、推断或判断 | 放入 Our take / Our View，说明依据、限制与不确定性 |

Claim 不是“假消息”的同义词。某公司“公布了提效 30% 的结果”可以是事实；“所有团队都能提效 30%”不能因此成立。模型抽取出的陈述默认是待核验内容，不能因格式正确就成为 Fact。

### 核验步骤

1. 列出决定标题和 So What 是否成立的关键陈述，逐条对应证据。
2. 优先打开原始发布、文档、论文、仓库、数据或完整采访；查看具体段落、表格、版本或视频时间码。
3. 检查主体、动作、时间、适用范围、数字分母、比较基线和限制。区分发布、预告、内测、可用与实际采用。
4. 追踪转述关系。多个媒体引用同一新闻稿，按一个来源根计算；转译、转载不能增加独立性。
5. 查冲突与更正。原文与标题不一致时按原文处理；不同来源有冲突时记录分歧，不能让模型取一个“平均说法”。
6. 给出通过 / 待核实 / 不通过，注明审核人及时间。关键缺口未解决，不发布依赖该缺口的结论。

Source / Evidence 是门槛，不是普通评分项。不能以“价值很高”“来自大公司”或“多数网站都这么说”为理由绕过。

### Primary Source 优先的具体用法

二手媒体主要承担发现、调查、补充背景和交叉验证。发现产品变化后，回到发布说明、文档或代码；发现人物观点后，回到原文、完整访谈及其上下文。

官方材料对“公司发布了什么”“公司怎样描述自己的结果”有直接证明力，对效果是否普遍成立、竞争对手是否落后或未来是否发生，不自动有证明力。

独立媒体原创调查、作者自己的实验或采访记录，可以是针对其获得材料的一手证据。不要把“官方未确认”作为排除可靠调查的唯一理由，也不能把匿名转述包装成已核实事实。

找不到可获得的一手材料时，常规发布信息先待核实。确有价值的原创调查或多条独立可靠报道，由编辑核对方法、来源链和局限后，决定是否以“据报道”的限定表达发布；必须记录例外理由。只有单条无法核查的传闻、搜索摘要或截图，不能支撑事实性标题。

**Discovery ≠ Truth。** 社区热帖、榜单、转发与短视频只提供核查入口。它们可以引导找原始材料，不直接为主张背书。只看到摘要、无法访问正文时，如实标记，不能让模型补齐细节。

### Evidence 最小记录

```text
Evidence ID：
针对的陈述 / Signal Thesis 版本：
来源 Item / 相关 Event：
原始 URL、作者、发布时间、访问时间：
原文定位：段落 / 表格 / 页码 / 视频时间码
原文要点或必要短摘录：
来源根 / 与其他材料的依赖关系：
方向：Supporting / Counter / Context
为何支持、反驳或仅提供背景：
方法、样本、适用范围与利益关联：
核验状态、审核人、审核时间：
更正 / 撤回 / 失效记录：
```

Supporting / Counter 是相对于特定主张的关系，不是材料永久标签。一个实验可能支持“在小型任务中有效”，同时反驳“在所有任务中普遍提效”。Context 不能计入支持证据数量。

## 4. 从 Items 聚成 Event

先给每个候选事件写一个事实骨架：**谁 + 做了什么 + 对什么对象 + 何时 + 哪个版本或范围**。

以下情况通常合并：官方公告、同次发布的社交帖、媒体转述和演示都指向同一个发布动作。保留每个 Item 的来源与差异，不用合并删除原始材料。

以下情况通常拆开：同一家公司的不同发布；同一产品不同日期的实质版本变化；产品发布与后续独立评测；不同组织的类似功能；研究结论与产品采用。Topic 相同、标题相似，不代表同一 Event。

一篇长访谈可以包含多个事件或观点。允许 Item 关联多个 Events，并保留各自段落或时间码。Voices 可用“某人在某访谈中提出某观点”作为 Event；这只确认发言发生，不确认观点为真。常青实践可用“作者发表了一项方法或复盘”组织，不伪造为今日新发布。

机器可以结合时间、Entity、动作、版本、引用 URL 和语义相似度提出聚类建议。人审核歧义，尤其防止把反证材料混成支持事件。合并、拆分都保留旧 ID 的映射和决定，已有 Brief / Evidence 的关联随之复查。

**演练：**某产品 v2 发布说明、创始人解读和五家媒体转述，合成一个发布 Event；三天后一家团队报告其在大型仓库中失败，建立另一个实测 Event。二者可以属于同一 Signal，不应因讨论相同产品而合并。

## 5. Editorial Judgment：四个问题怎样回答

| 维度 | 编辑要写出的内容 | 常见失败与处理 |
|---|---|---|
| Change | “之前是 A，现在在条件 C 下变成 B”，附比较依据 | 只有“又更新了”就回查基线；基线未知则明确未知，缩小标题 |
| Signal | 关联哪个 Thesis 的哪一部分，是支持、反驳还是暂时无关 | 只有同一 Topic 不够；不得强行关联或把观点当采用数据 |
| Half-life | 预期价值持续时间、过时触发条件与复查时点 | 长半衰期只是优先因素；短期紧迫信息可以收，需说明时效 |
| So What | “对某类读者，这意味着可以/需要/开始理解……” | 只有“推动 AI 发展”不通过；无法具体说明就暂缓 Brief |

Half-life 可记为短期（约一天）、近期（约一周）、持续（约三个月）、长期（约一年及以上），只是编辑估计，不是科学预测或保证。技术实践尤其要标版本；旧实践重新出现时，核验当前适用性。

四个问题不求总分。一个足够 Useful 的实践可写“暂无 Signal 关联”；一条 Important 内容可写“暂无直接行动建议”。避免为了填齐字段虚构结论。

### 什么时候形成 Brief

至少一条价值路径成立、关键事实通过 Quality Gate、能清楚回答 So What，而且相对已有内容存在新增价值，才写成 Brief。只是重复同一事件时更新已有 Brief；新增独立事实且改变理解时，才另建 Brief 并关联旧内容。

有助于检验 Signal 却不值得单独阅读的材料，走仅存证。一个值得记录的 Event 不必得到一个 Brief。

## 6. Brief 的写法与交付模板

建议每条 1–3 分钟可读。标题直接表达最值得知道的变化，不能超过证据能支撑的范围。结构稳定，但相邻栏目不要重复说同一句话。

```text
Brief ID / 标题：
状态：Draft / In Review / Approved / Published / Withdrawn
关联 Event IDs：
Coverage / Topic / Entity：
Value Gate：Important [理由]；Useful [理由]；结论
Quality Gate：结论；未决问题（如有）

What happened
已核实发生了什么；Claim 明确注明谁说的、在什么条件下。

Why it matters
为什么值得特定读者关注，影响什么。

What changed
与过去的可比基线有什么变化；未知之处明确写出。

Our take
Less 的解释、推断及局限，避免把趋势假设写成事实。

Try it（偏 Useful 时）
适合谁；版本和前提；最小尝试步骤；预期观察；成本与限制；
是否实际试用、由谁在何种环境验证。未试用不得写成亲测。

Sources
原始出处优先；每个关键陈述指向具体 Evidence / 原文定位。

Related signals（可为空）
Signal ID；证据方向；为何关联。

编辑 / 审核人 / 审核时间 / 内容版本：
发布 / 更新 / 更正记录：
```

Facts 与 Interpretation 在内部字段分开，在阅读表达上也要分开。Sources 不能只列域名首页或搜索页。翻译人物观点时，保留原文定位和限定语；意译不加引号冒充逐字引述。

### 三个执行示例

**例 A：重要但不能马上用。** 假设一个研究团队公开了新评估结果，表明某类长任务能力在特定测试中明显改善。Important 可能强，Useful 暂时弱。先核查任务定义、基线、样本和失败率；可写“在该评估上改善”，不能写“已能自主承担所有软件工程”。若方法缺失，待核实，不因论文热度通过质量门。

**例 B：有用但行业影响有限。** 假设某工程师公开 Context 管理实践，在说明仓库规模、工具版本和成本后给出可复现对照。Useful 可强，Important 可弱。编辑核验代码与实验条件；Brief 的 Try it 写清适合谁、如何观察收益。无需宣称它证明行业已经进入新阶段。

**例 C：热门但不收。** 假设一个仓库突然获得大量 Star，只有效果演示，没有可运行内容、适用条件或独立验证。它是 Discovery 线索；“大量关注”不证明 Useful。暂缓，寻找作者材料和复现结果；找不到则不发。

## 7. Signal 建立与持续修正

### 建立前先写可检验的 Thesis

Signal 的定义及字段见[蓝图第 9 节](01-product-blueprint.md#9-signal长期资产的基本单位)。新建时必须写：观察到的变化、适用人群/任务/场景、时间范围、已有解释，以及什么结果会削弱或推翻判断。

“Agentic Software Engineering”可作名称，不能代替 Thesis。首期可以检验：“在边界清楚、可自动验证的软件工程任务中，部分团队开始从逐步提示转向任务委派与人工验收。”这仍是候选假设，不预设行业结论。

建 Candidate 至少需要一个可定位的起始证据与清楚的后续观察计划。它允许证据不足，但不对外表现成成熟判断。Supporting Evidence 和 Counter Evidence 两栏从第一天就建立。

### 状态的操作口径

以下是 v0.1 的编辑执行规则，可以通过真实案例修订。证据数量只是最低检查，不是升级公式。

| 状态 | 进入 / 保持条件 | 不能据此升级 |
|---|---|---|
| Candidate | 有可证伪 Thesis、起始证据、反证搜索计划与责任人 | 一个发布、一个热点、一个人的预测 |
| Emerging | 至少两个不同 Events、至少两个独立来源根提供相互关联的证据；完成一轮反证检索；范围明确 | 多家转载同一公告；多个产品发布直接证明普遍提效 |
| Strong | 跨时间、独立主体与不同证据类型形成较稳支持；若 Thesis 涉及采用或效果，必须有对应行为或结果证据 | 发布数量、人物认同、演示成功、Benchmark 单点增长 |
| Established | 在明确范围和观察期内有持续独立验证，主要替代解释和重要反证已被处理 | 仅因运营时间变长或缺少反对声 |
| Weakening | 新证据降低解释力、核心支持失效，或预定应出现的结果未出现 | 只因近期没新闻；“没有新增”需与预设观察条件比较 |
| Rejected | 核心判断被可靠证据否定，或在事先声明的范围/检验条件下不成立 | 为整理界面或隐藏错误而删除 |

任何成熟度均可下降；关键反证可以直接导致 Rejected。Weakening 可在新证据充分时恢复到适当状态，必须留下恢复原因。Thesis 范围发生实质变化时创建新版本，不能把原来的失败改写成从未提出过。

### 每次 Signal Review 的动作

1. 阅读新材料，判断独立性和适用范围；回到原文而非只看已有 Brief。
2. 主动查找反面结果：失败实验、低采用、成本增加、Review 负担、回归旧流程和替代解释。不能只用支持 Thesis 的关键词检索。
3. 将材料标为 Supporting / Counter / Context，写明针对 Thesis 哪一部分。一个弱负面案例不自动推翻整体，但不得忽略它揭示的边界。
4. 比较当前解释与替代解释，决定保持、收窄、增强、弱化或否定。重要的状态变化由人批准。
5. 更新 Our View、Timeline 和 Last Updated；保留旧状态、旧 Thesis、证据依据、审核人和变更理由。

没有找到 Counter Evidence 时，写“在本次检索范围内暂未找到”，并记录检索词、来源类型、日期与缺口。不能写“没有反证，因此成立”。Counter Evidence 栏存在不等于真正完成了反证工作。

重大反证、来源撤回、关键实验复现失败，进入当日优先 Review；平时至少每周复评正在跟踪的 Signal。自动发现新材料不更新 Last Updated，只有实质复评才更新；最近检查时间可另记。

### Signal 更新模板

```text
Signal ID / Thesis 版本 / 本次日期 / 审核人：
旧状态 → 建议新状态：
新增 Supporting Evidence：
新增 Counter Evidence：
本轮主动反证检索：范围、查询、发现与缺口
来源独立性与证据适用范围：
替代解释：
Our View：现在怎么看，哪些仍不知道
决定及原因：保持 / 收窄 / 升级 / 弱化 / 否定
下一次观察或复查条件：
Timeline 记录 / Last Updated：
```

**演练：**三个厂商发布任务委派功能，只能支持“产品交互开始变化”。随后若独立团队报告在大型仓库中 Review 时间增加，这应进入 Counter Evidence，限制“普遍提高效率”的主张；编辑可能保留交互变化判断，同时将效率判断维持 Candidate 或标为 Weakening。不能把所有不同命题塞进一个永远被支持的 Signal。

## 8. 每日运行与人工 Review

### 每日操作

1. 查看来源健康状况，区分“今天无新内容”和“采集失败”；记录观察截止时间。
2. 审核候选与 Event 聚类，补看少量被机器淘汰的内容，发现漏选。
3. 先做 Value Gate，再做 Quality Gate；候选队列可以少，不能为得到 20 个 Candidate 加入低价值内容。
4. 对通过者判断 So What，写 Brief；待核实者指定下一步，仅存证者进入 Signal Review。
5. 完成人工发布检查，生成内部 Today；今天只有 3 条值得看就只发 3 条，不够则如实记录。
6. 处理新增正反证据、来源更正和 Signal 更新；记录总编辑时间、卡点和漏选。

观察截止时间与阅读节奏在 Week 1 固定并写入运行记录。旧内容不能伪装成当天新闻；有必要的迟到信息标明原始日期。每日结束不清空未解决事项。

### 人和机器的责任

| 工作 | 机器可做 | 人必须决定 |
|---|---|---|
| 采集与 Normalize | 获取、提取、翻译、标注出处 | 抽查偏差；关键事实在发布前核对 |
| 聚类与候选 | 建议合并、排序、给出理由 | 处理歧义、纠正漏选和错选 |
| Quality Gate | 找原始来源、标冲突和缺口 | 关键证据是否充分、例外是否可接受 |
| Brief | 起草结构与措辞 | 标题、So What、事实边界、最终批准 |
| Signal | 提出关联、搜正反证据、草拟更新 | 建立、改变 Thesis、状态升降与拒绝 |
| 更正 | 找受影响的关联内容 | 更正范围、撤回及对读者的解释 |

“机器负责发现，人负责判断”落实为发布动作和 Signal 状态变更都需要显式人工批准。首期同一人兼任编辑与审核时，也分别完成草稿与复核两步，并保留时间和决定；不能用 AI 自检冒充第二个人审核。

### 发布前检查

- [ ] Important 或 Useful 至少一项有具体理由，So What 不是空泛赞美。
- [ ] 标题和关键事实逐条对应 Evidence；原始材料已经实际查看。
- [ ] 日期、版本、数量、基线和适用条件无误；已处理同源转载与冲突。
- [ ] Fact / Claim / Interpretation 清楚分离，未把作者自述写成普遍事实。
- [ ] 聚类正确，不是已有 Brief 的重复；新增价值明确。
- [ ] Useful 的试用状态如实标注；Signal 关联方向与限制明确。
- [ ] 审核人、版本、批准时间和内部发布状态已记录。

不确定且可能改变核心结论时暂缓。可以删除缺乏依据的非关键句后重新审核，但若核心 So What 因此消失，就不再发布该 Brief。

## 9. 更正、复盘与规则维护

发现错误后，先停止继续分发受影响结论，核实错误范围，再修订 Brief。若核心结论不成立，标记 Withdrawn；保留原版本、更正时间、原因及替代版本。同步检查相关 Event、Evidence 与 Signal，不能只改文章正文。

对于来源修改、撤稿或页面失效，保留已有抓取版本与访问记录，标出当前状态，重新评估可用性。失效链接不必然意味着事实为假，但用户必须知道当前能否复查以及证据是否被撤回。

每周复盘少量边界案例：错选、漏选、同源误当独立、聚类错合/错拆、推断越界、反证遗漏及耗时最高的步骤。每次规则变化写明案例、旧规则、新规则、影响范围；保存前后标注用于检查是否真的改善。漏选样本的抽样和指标口径由[MVP 第 6 节](03-phase-1-content-engine-mvp.md#6-验证指标与结束条件)维护。

规则变化可以调整执行阈值，不能悄悄改变 OR、独立 Quality Gate、人工批准和反证记录等产品基线。涉及这些原则时，先更新蓝图并取得项目负责人决定。
